## The conclusions that matter, all measured

**The one-line distinction Sean landed on and likes:**
> A loop **discovers** what to do next. A graph **pre-determines** what happens next.

**Loop wins** when you cannot draw the steps in advance — "debug why my test is
failing", where every step depends on what the last one found. That is most of
what waku does.

**Graph wins** when you already know the shape and steps can overlap.

**Sean's own realisation, and the strongest hook in the material:**
> He opened waku's existing architecture diagram — gateway → memory → loop →
> tools → reply, fixed order every turn — and said *"that's a graph. i just had it
> hardcoded in python instead of nodes and edges."*
>
> So a graph engine does not give you the shape. You already had it. It makes the
> shape **data instead of code**: inspectable, drawable from the code itself,
> partly parallel, re-routable without rewriting the function.

**The skeptical framing he wants to lead with** (his instinct, and correct):
> "Isn't this just 'deterministic workflow' vs 'let the agent decide' from 2023?"
> Mostly yes. Airflow/Temporal/Step Functions have done conditional parallel DAGs
> for a decade. What is genuinely new is narrow: **(1) the nodes are
> non-deterministic, (2) a model can pick the edge, (3) so you need guardrails
> Airflow never needed** — waku's engine caps visits per node and total steps.
> Old shape, new contents.

**Context:** Peter Steinberger (@steipete) posted twelve words on 2026-07-18 —
*"Are we still talking loops or did we shift to graphs yet?"* — 2.9M views. He did
not define anything; he poked the field. Andrew Ng's graph course reignited it.
The emerging consensus — *graphs extend loops, the loop becomes one node* — is
exactly what waku's `full_agent` node does.

## The use cases to document (ranked by how well they'd demo)

**1. Multi-calendar read — the BEST one, and it is real.**
Sean has Apple + Google + waku's local calendar. Loop: model calls one tool, reads
the result, decides to call another, three sequential round trips. Graph: fan out
to all three at once, merge, answer.
- Google API measured at **0.39s**; AppleScript at **~12s**. Real parallelism, real numbers.
- Half of it already exists: `waku/tools/calendar.py::make_list_tool` now merges
  Google + local (shipped in #40).
- Building this as a graph workflow fixes a real problem AND makes the demo obvious.

**2. Morning brief — three genuinely different branches.**
calendar ∥ memory search (FTS5) ∥ outbox → synthesize → router: anything urgent?
`waku/ops/brief.py` already exists as a starting point.

**3. Fact-check my memory — the only way to exercise bounded cycles.**
pick a fact → search web → judge → (outdated → update → re-judge, `max_visits=2`).
Sean's memory has ~36 facts and some are stale, so it does something real.

**Weak examples, say so honestly:** triage (shipped, but its parallelism saves
40ms); the content workflow from design doc §4.2 (blocked — it needs `human_node`,
which does not exist in `waku/graph/nodes.py`).

## What is missing or could be improved

**1. Tool test coverage is the biggest hole.** 7 of 13 registered tools have ZERO
test references: `browse_web`, `create_note`, `create_reminder`, `list_events`,
`read_apple_mail`, `schedule_task`, `send_message`. `list_events` is the tool that
told Sean his calendar was empty while his real Thursday was full.

**2. The eval suite cannot see reality.** It tests string generation, never whether
a call succeeds. That is why every Apple tool was broken for weeks while CI stayed
green. The old test literally said *"covered by ... manual verification on the dev
machine"*. `evals/deterministic/test_apple_tools.py` (new) pins what CAN be checked
offline; the structural gap remains.

**3. `waku/ops/dashboard.py` is still the largest file** (~893 lines after the split).

**4. Apple Mail is genuinely unusable** — Mail.app cannot answer
`count of messages of inbox` inside two minutes (`-1712`). Documented, fails fast
in 20s with an honest message. Not our bug.

**5. `WAKU_APPLE_TOOLS=1` costs ~13s per calendar question** for one line Google
already has. Consider turning it off in `.env`, or folding Apple into `list_events`
behind a local-calendars-only filter.

**6. Google Calendar has no shipped OAuth client yet** — `CLIENT_ID`/`CLIENT_SECRET`
in `waku/tools/google_calendar.py` are empty stubs. PR #42 addresses this.
Decision already taken: **readonly scope** for the shipped client; write access
stays behind the user's own `.waku/credentials.json`.

**7. `.venv` was destroyed** by a stray `ln -sfn` during worktree cleanup and had to
be rebuilt. If anything imports oddly, rebuild:
`uv venv --python 3.11 && VIRTUAL_ENV=$PWD/.venv uv pip install -e '.[dev,eval,gcal]'`
